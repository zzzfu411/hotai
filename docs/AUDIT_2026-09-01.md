### 2.1 代码和数据流

Hot AI 有两条刻意分开的内容链路：

```text
浏览器 -> /api/catalog/pull -> allowlisted RSS/Atom/JSON Feed -> / (NookFeed)
                                      (不写 Article)

Fetcher cron -> Source -> fetch/parse -> retention -> dedupe/score -> Article
            -> AI lease/retry -> Digest -> /api/revalidate
浏览器/页面 -> Prisma queries -> /hot、/digest、/a/[id]、分类/来源页
浏览器 -> /api/ask -> AskCache + PostgreSQL AskDailyUsage/AskReservation -> SSE
```

主要信任边界和 sink：

| 边界 | 当前控制 |
|---|---|
| 用户提交 URL 到代理/阅读器 | scheme、凭据、literal/private/metadata 地址、DNS answer、重定向、超时和响应字节上限；请求使用 pinned DNS agent，DNS memo 有 512 项硬上限 |
| RSS/Atom/JSON/Juya HTML 到浏览器 | DOMPurify/linkedom、禁止脚本/样式/高风险标签，二次过滤 `href/src/srcset`，仅保留安全 HTTP(S) |
| 外部 feed 字段到 DB/Feed/OPML | 写入前 retention、URL/字段归一化；公共输出再次使用 `safeShareableHttpUrl`；DNS alias 需按部署策略另验 |
| 匿名 Ask 到 AI 供应商 | 请求体限长、IP/Nginx 限流、AskCache、PostgreSQL 原子 token/并发预约、TTL 和断连结算 |
| Fetcher 到上游/DB | timeout/响应体上限、周期 lease、来源健康、失败计数、AI CAS/lease/retry；Source URL 仍是运维输入 |
| 运维 secret 到 revalidate/metrics/AI | revalidate secret + path allowlist、metrics Bearer timing-safe compare、AI 第三方/HTTP 显式 opt-in |

## 4. 安全审计状态

完整安全证据见 [`docs/security-audit/run-3/REPORT.md`](security-audit/run-3/REPORT.md)、[`FINDINGS-DETAIL.md`](security-audit/run-3/FINDINGS-DETAIL.md) 和 [`findings.json`](security-audit/run-3/findings.json)。结论如下：

| 项目 | 当前结论 |
|---|---|
| 当前代码中的 confirmed finding | **0** |
| 历史 SEC-01：AI relay/credential 错误路由 | 已修复：示例为空、placeholder/双凭据拒绝、非官方 relay 显式 opt-in |
| 历史 SEC-02：伪造左侧 XFF 绕过限流 | 已修复：Nginx 覆盖 header，应用只采用受信地址，公共 limiter 有容量上限 |
| 历史 SEC-03：Juya inline CSS 视口覆盖 | 已修复：远程 HTML 禁止 `style` 并二次过滤 URL sink |
| 历史 Ask 欠记账候选 | 已修复：abort、SSE enqueue 失败、provider 异常均全额结算预约；估算改为 UTF-8 bytes/2 |
| 本轮被拒绝候选 | `javascript:`/私网 feed 图片等在当前边界被过滤；不能据此报告漏洞 |

残余 hardening（不是 confirmed finding）：

- 尚未配置 CSP nonce；当前响应头先加入 `nosniff`、`Referrer-Policy`、`X-Frame-Options` 和 `Permissions-Policy`，CSP 需在内联主题脚本迁移后加入。
- Fetcher 的 Source URL 是运维信任输入，不是匿名用户输入；若未来开放源管理 API，必须把同一 SSRF policy 延伸到该入口。
- 多层 CDN/Cloudflare 接入时不能继续盲信任任意客户端 header，需按官方出口网段重新定义真实 IP。
- 浏览器访问时的 DNS 重新解析无法完全由服务端同步策略替代，高敏部署应结合图片代理、CSP 和网络隔离。
- 持久化 Article/crossPost 外链只做语法和明显私网过滤；类似 `127.0.0.1.nip.io` 的 DNS alias 不在当前离线检查能力内，应在 staging 的网络策略和浏览器行为中单独验证。
