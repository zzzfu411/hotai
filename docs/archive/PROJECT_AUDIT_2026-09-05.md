## 3. 当前产品与架构的真实形态

### 3.1 两套内容系统，三类阅读方式

```text
外部 RSS / Atom / JSON Feed
    → /api/catalog/pull → 服务端 Feed 缓存 → 客户端 NookFeed
    → 综合/要闻：编辑评分 + 事件聚合 + 首屏多样性
    → 其他频道：发布时间排序
    → /r?url=... → /api/readability → 清洗正文

编辑 Source → fetcher → 去重/评分 → Article（默认保留 14 天）
    → AI 摘要与重要度 → 全量重算 → 热榜/分类/搜索/Feed
    → Digest（Web 可按需兜底生成）
    → Ask（48h 内最多 25 篇高分文章）
    → /a/[id] → AI 摘要 + 阅读标记 + 正文抽取

用户 OPML / 自定义 RSS → localStorage → /api/proxy/feed
    → 本机订阅列表 → 当前直接打开外部原文
```

“实时速闻不写 Article”成立；“实时速闻不依赖 Postgres”不成立。公开抓取限流本身访问 Postgres，这一运行依赖必须纳入架构图。

## 4. 问题清单与证据

优先级含义：**P1**＝优先修复的主要路径／发布风险；**P2**＝功能完整性、可恢复性或可靠性问题；**P3**＝体验、语义和维护改进。未发现本次证据足以认定的 P0 项，但这不等于对生产安全作出保证。

### F01 · P1 · 实时首页受数据库故障阻断，错误反馈却指向来源

**证据等级：已复现 + 代码确认。**

本地首页请求 `/api/catalog/pull` 返回 503，服务日志说明共享限流器连接不到数据库。页面显示“00 在线源、00 条信号、15 异常”和“时间线拉取失败”。实际尚未验证这 15 个源是否在线，不能把请求层失败当成每源失败。

原因：[catalog/pull:159](D:/Develop/claude/hotai/apps/web/app/api/catalog/pull/route.ts:159) 在拉源前调用数据库限流；[NookFeed:481](D:/Develop/claude/hotai/apps/web/components/NookFeed.tsx:481) 在非成功响应时把失败数设为全部源数。热榜、搜索、简报故障提示仍告诉用户速闻可用，形成错误恢复建议。

**建议：**保留故障时拒绝新增抓取的保护。分开表示“服务不可用”和“来源失败”；优先显示已有快照及时间。若产品确实要求 DB 故障时首页仍可用，应设计不依赖业务 DB 的有界限流或预生成快照，不能直接绕过限流。

**验收：**DB 断开时页面显示服务故障且不伪造源健康；有缓存时可读并标注过期；所有跳转建议与实际依赖一致。

### F02 · P1 · 手动刷新仍冻结已显示条目的顺序

**证据等级：代码确认。**

已有缓存时，`keepCachedDuringStream=true`，`editorialSettled` 同时为 true。完整拉取最终执行 `publish(complete, false)`，使用 `preserveVisiblePrefix` 把旧可见条目按旧顺序放回前缀。用户明确按刷新按钮，也不能让新头条超越仍存在的旧前缀；非编辑频道也可能不再严格倒序。

依据：[NookFeed:419](D:/Develop/claude/hotai/apps/web/components/NookFeed.tsx:419)、[NookFeed:518](D:/Develop/claude/hotai/apps/web/components/NookFeed.tsx:518)、[progressive-list:5](D:/Develop/claude/hotai/apps/web/lib/progressive-list.ts:5)。例：旧列表 `[A,B]`，新结果 `[C,A,B]`，保留两条前缀后会显示 `[A,B,C]`。

**建议：**历史返回保留阅读位置，后台更新显示“有 N 条新内容”，主动刷新则应用新排序。行为策略应显式传递，不能只根据缓存是否存在决定。

**验收：**同一组数据分别测试后台更新、历史返回、手动刷新；只有前两种允许保留旧顺序，新频道最新文章在主动刷新后置顶。

### F03 · P2 · 手机端订阅表单的标签与输入框错位

**证据等级：390×844 浏览器已复现。**

实际排列为“Feed 地址标签 → 名称标签 → 名称输入框 → Feed 地址输入框”。[globals.css:3031](D:/Develop/claude/hotai/apps/web/app/globals.css:3031) 的手机媒体查询给所有 `.kz-search` 设置 `order:3`；订阅页把地址输入组件也放在该 class 内，而父容器是纵向 flex。

**建议：**把页头换行规则收窄到 `.kz-topbar-row > .kz-search`，表单布局使用自身 class。不要用修改 DOM 标签顺序补偿全局样式污染。

**验收：**320、390、720、768px 中文／英文检查标签、控件、Tab 顺序一致；同时回归搜索页和 Ask 输入框。

### F04 · P2 · “稍后读／已读”缺少取回与列表反馈闭环

**证据等级：代码确认。**

[Reader:123](D:/Develop/claude/hotai/apps/web/components/Reader.tsx:123) 可记录数值 Article ID；[reading-flags](D:/Develop/claude/hotai/apps/web/lib/reading-flags.ts) 的读取只用于阅读器按钮。路由和列表没有稍后读汇总入口，ArticleCard 也不反映已读状态。默认首页的 `/r` 不提供标记。

**建议：**在“我的”中增加稍后读列表，用现有本机存储实现。条目保留标题和原文 URL 等最小本机快照，明确站内 Article 14 天过期后仍可打开原文，不需要延长数据库保留期。

**验收：**保存后可从“我的”找到；跨页状态一致；过期 Article 有清晰回退；实时条目使用 URL 身份或明确说明不支持。

### F05 · P2 · 首页内部 Hot AI Feed 被错误送进远程阅读器

**证据等级：代码确认；实际正文影响需有数据时复测。**

[catalog/pull:63](D:/Develop/claude/hotai/apps/web/app/api/catalog/pull/route.ts:63) 为内部源生成站内 `/a/{id}` 的绝对地址；但 [NookFeed:155](D:/Develop/claude/hotai/apps/web/components/NookFeed.tsx:155) 的 `readerHref` 只特殊处理橘鸦，其余一律封装成 `/r?url=...`。

结果是“用远程正文抽取服务再次读取本站的阅读壳”。它无法等同于直接进入 `/a/[id]`，会遗漏 AI 摘要／阅读标记等专属体验，并增加回环 HTTP；若 SITE URL 为本机地址，还会遇到公共 URL 校验限制。

**建议：**内部源返回显式 `articleId` 或安全的站内 href，客户端直接路由；不要仅依赖任意 URL 前缀猜测身份。

**验收：**首页 AI 频道的内部条目直接进入 `/a/{id}`，不向 readability 提交本站阅读页地址。

### F06 · P2 · OPML“选择文件”缺少键盘可操作控件

**证据等级：DOM + 代码确认。**

[SubscribeClient:448](D:/Develop/claude/hotai/apps/web/components/SubscribeClient.tsx:448) 使用普通 label 包裹 `hidden` 文件 input。label 没有可聚焦语义，隐藏 input 也无法 Tab 聚焦；浏览器可访问性树把“选择文件”显示为 generic，而非按钮。

**建议：**用真实按钮触发文件 input，或保留可聚焦、视觉隐藏的原生 file input 并提供焦点样式。

**验收：**仅用 Tab 和 Enter/Space 可以选择 OPML 文件，焦点可见且名称明确。

### F07 · P2 · 本机存储失败仍显示添加／保存成功

**证据等级：代码确认；条件为存储被禁止或额度耗尽。**

[local-sources:151](D:/Develop/claude/hotai/apps/web/lib/local-sources.ts:151) 与 [reading-flags:46](D:/Develop/claude/hotai/apps/web/lib/reading-flags.ts:46) 吞掉 `setItem` 异常；UI 继续更新状态、提示已添加或已稍后。刷新后数据消失，用户无法知道从未持久化。

**建议：**保存返回结果；失败时标记“仅本次会话有效”，给出导出入口。批量更新阅读状态也应避免一半成功一半失败。

**验收：**模拟抛出 QuotaExceededError，页面不承诺已持久保存，已有数据不被清空。

### F08 · P2 · Ask 流异常结束可能把半截回答显示为已完成

**证据等级：代码确认。**

[AskBox:110](D:/Develop/claude/hotai/apps/web/components/AskBox.tsx:110) 遇到 reader EOF 直接 break，finally 关闭 busy；没有要求收到 `obj.done`。连接在最后一帧前关闭时，半截回答没有“不完整”标记。流尾缓冲也没有单独完整性处理。

**建议：**记录完成帧和错误帧，EOF 未完成时显示可重试错误；保留部分内容但注明未完成。给流状态增加适当 aria-live 反馈。

**验收：**正常结束、仅有 delta 后断流、服务端 error、取消请求四种路径能清楚区分。

### F09 · P2 · 搜索控件状态只在首次挂载时读取 URL 对应参数

**证据等级：代码确认；浏览器历史恢复的完整复现尚待稳定生产模式验证。**

[SearchBox:24](D:/Develop/claude/hotai/apps/web/components/SearchBox.tsx:24) 以 props 初始化 q/sort，未在 props 更新时同步；同一路由的客户端导航可能保留组件，导致结果说明使用新 `initialQuery`，输入框或排序选中态仍为旧值。

**建议：**以 URL 为已提交查询的单一来源，输入草稿与提交状态分离；历史导航同步草稿及排序。不要用每次渲染重设 state。

**验收：**A 搜索 → B 搜索 → 后退／前进，URL、输入框、排序和结果标签一致。

### 5.3 前端状态与组件边界

NookFeed 集中承担数据校验、缓存、排序、流解析、历史恢复、滚动定位和渲染。它已有不少精细保护，盲目重写风险较高。合理拆分顺序是：先提炼刷新策略与状态机，再把浏览历史恢复单独封装，最后分离展示组件。

## 6. 内容逻辑、AI 与数据层专项分析

### 6.1 热榜评分

实际公式为：

```text
score = (sourceWeight + signalBoost + keywordBoost + aiImportance × weight)
        × timeDecay + sourceWeight × 0.1
```

它是加权相加再衰减，并不是文案常写的各项相乘。AI importance 默认最多贡献约 2 分，互动信号经 log1p 后在高互动源可显著更大，因此“按重要度”不能被解释为单按 AI importance 排序。

这不自动构成算法错误：统一权重、时间衰减和互动本身有合理性。但要验证来源间尺度是否偏斜。建议基于真实样本统计各分量占比，检查官方低互动公告与高下载模型的相对位置，建立小型人工排序评估集，而不是只看公式单元测试。

Hugging Face trending 对超过 30 天的日期替换为当前时间，是明确的产品取舍。更清楚的数据模型应区分“原始发布时间”和“本次被观察为趋势的时间”，避免用户把旧模型理解为刚发布。该调整应连同 URL 去重和 14 天清理一起评估，不宜只改一个日期字段。

### 6.2 首页编辑排序

已有标题归一化、中英词法特征、事件聚类、来源共现加分、低价值内容减分和首屏来源多样性。优势是无需付费模型也能产生较有层次的首页。

局限包括：

- 聚类是词法相似，跨语言改写和相近事件可能误分／误合。
- 共现计数使用 sourceId；同一聚合服务的多个频道不等同于多个独立新闻机构。
- 英文关键词存在子串匹配，短片段可能影响不相关单词。
- 来源权重是硬编码编辑判断，没有对用户展示解释。
- 聚类比较及每次流更新重复排序存在超线性成本；默认最多 20×24 条，规模尚有上限，需先量测再优化。

建议将其对外称为“编辑精选／综合排序”，提供“最新”入口。若排序错误，增加真实反例测试，不应无依据地继续堆关键词。

### 6.3 去重与保留

URL 规范化、arXiv 统一、标题窗口去重、crossPosts 合并和 signals 逐项取 max 已有实现，能有效减少重复。顺序持久化有助于让后续源看到前序去重结果。

需要接受并明确的边界：不是语义级去重；同 URL 内容更新与标题改写不必然对应新的事件；Article 硬删除后站内分享链接会失效。这些是短期热榜设计的成本，不能为了“修复 404”擅自改为永久归档。

数据库具备 score、source/date、publishedAt、titleHash、AI 状态和主题 GIN 等索引。分类查询现按 publishedAt 排序，现有 category/score 索引并非完全对应；是否新增 category/publishedAt 复合索引应先跑真实 `EXPLAIN ANALYZE`。搜索 contains/ILIKE 没有全文或 trigram 索引，但 14 天小语料不应直接判定不可用。

### 6.4 AI 成本与质量

现有优点：AI 可关闭；供应商配置显式校验；enrich 有批处理、单篇回退、重试和 CAS；Ask 有日预算、并发预约、相同问题 single-flight、引用快照；Digest URL/ID 关联受输入约束。

仍需运营验证：

- enrich 每周期处理数量只是容量上限，不保证高峰期所有新文章在过期前处理完成；长期按分数优先可能让低分文章饥饿。
- 摘要输入通常来自 RSS 摘要而非完整文章，不能宣传为“全文事实核验”。
- AI 重要度是模型评分，尚无校准集、误差分布或人工抽查证据。
- 每周期批处理失败转单篇可显著增加调用数；Ask token 预算并不是全站 AI 总账，enrich/digest 应独立统计消耗。
- 关闭摘要生成与隐藏 Ask 是不同开关语义，UI 应分别展示功能状态。

建议监控 pending 最老年龄、入库到摘要完成的 P95 延迟、失败比例、批次回退比例及各 AI 路径 token 消耗。不要仅记录成功总数。

## 7. 可靠性、部署与保护边界

### 7.1 已有且应保留的措施

- Public fetch 对协议、私网目标、DNS 和重定向有检查，限制响应大小与超时。
- Readability 输出经过 DOMPurify 和 URL 属性清洗；禁止脚本、iframe、表单等标签，并移除 srcset、内联 style。
- 公开抓取接口共享数据库限流，数据库不可达时拒绝新增工作。
- Ask 配额和协调状态持久化，供应商失败或中断按保守方式结算。
- Nginx 覆盖代理 IP 头，PM2 Web 绑定 loopback；当前配置中这一信任边界是连贯的。
- metrics 默认需要 token；有 liveness 与 readiness 区分。
- CI 有数据库 service、迁移、种子、类型检查、Lint、构建、编译产物 smoke 和依赖审计配置。
- 部署文档已有备份、恢复演练和回滚章节，不能把“没有备份方案”列为发现。

### 7.2 需要进一步验证的风险

1. **容量瓶颈。** 同一限流 namespace 共用 PostgreSQL advisory lock，而且请求内清理和计数；准确性好，但同接口所有 IP 争用同一把锁。需用并发测试确认延迟拐点。
2. **缓存在多实例间不共享。** Feed/Readability 缓存和合并请求是进程内的；当前 PM2 单实例合理，多实例部署需重新核算上游请求量与内存。
3. **进程资源上限。** Web 512M、fetcher 256M 的 PM2 重启阈值是配置事实；没有 RSS、HTML 解析高峰实测，不能认定足够或不足。
4. **默认主页缺合成监控。** 存活不代表能读到新闻，需要实际验证条目数量和首条显示时间。
5. **防护不等同于正式安全结论。** CSP 当前明确未启用，可作为后续防御增强；本次未证实可利用 XSS/SSRF，不把缺少 CSP 单独描述为已发现漏洞。
6. **离线承诺。** 有 manifest 不等于有离线阅读。应在产品范围中明确安装外壳与内容离线的区别。
