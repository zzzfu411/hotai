# HotAI 新闻工作流审计与改进方案

审计日期：2026-09-01
范围：仓库当前 `main` 工作树；不依赖外网、不改变产品的无账户与文章 14 天保留边界。

## 1. 审计方法

本次采用三条相互独立的审查线，再由主任务汇总交叉验证（diversity intelligence）：

| 视角 | 重点 | 独立结论 |
| --- | --- | --- |
| 产品与 UX | 信息架构、用户旅程、空状态、阅读闭环 | 实时速闻、入库热榜、搜索的语义边界没有被用户看见；简报和 Ask 缺少可验证回链 |
| 抓取与数据链路 | RSS/适配器、持久化、健康状态、周期编排 | 空响应、部分持久化失败和周期关键阶段失败可能被报成成功；缓存 stale-if-error 会滑动续期 |
| 可靠性与安全 | 输入边界、并发、成本、故障隔离 | 外部 feed 字段无统一上限；Ask 缓存未做跨实例 miss 合并；若干健康/部署信号仍偏乐观 |

审计证据以源码、现有测试、`CLAUDE.md`、`docs/design.md` 和最近安全审计报告为准。当前本地没有可用 PostgreSQL，因此数据库集成路径和 Next 静态生成只能做源码/单元层验证，不能把“本地无法连接数据库”误判成应用逻辑通过。

## 2. 当前系统与用户旅程

### 2.1 数据流

```text
外部 RSS/Atom/JSON/抓取页
        |
        +--> 首页 /api/catalog/pull --> 浏览器实时速闻（不写 Article）
        |
        +--> fetcher cycle: purge -> fetch -> persist/dedupe/score
                                      -> AI enrich -> digest -> revalidate
                                      |
                                      +--> Article（保留 14 天）
                                      +--> Digest / AskCache / health
```

这条架构本身是清楚的：实时目录追求低延迟，Hot AI 追求可排序、可搜索、可生成简报的稳定语料。但 UI 目前把两种数据看起来像同一个“新闻池”，造成以下预期落差：

1. 用户在首页看到的实时条目，马上去 `/search` 找不到。
2. `/hot` 的“今日热榜”实际查询的是最近 14 天窗口内的全局热度，不是 24 小时榜。
3. `/search`、`/category` 和 `/hot` 使用 Article 数据；首页分类使用 Catalog source 数据，分类名和覆盖范围也不完全相同。
4. Digest 旧数据只留下外部 hostname 链接，用户无法顺畅回到站内文章详情；新生成的 digest 已补存文章 ID，并对旧行做 URL 回链推导。
5. Ask 让模型输出 `[n]` 引用，但旧 SSE 合同只传文本，没有传 corpus 元数据，前端无法验证或点击引用；本轮已补来源事件与缓存快照。

### 2.2 主要失败路径

| 路径 | 当前表现 | 用户/运营影响 |
| --- | --- | --- |
| 上游失败且已有缓存 | stale 条目在每次失败时刷新 `at` | 连续失败可无限提供过期内容，健康判断失真 |
| RSS/API 返回空数组 | 只有 scrape 空数组被当作失败 | 失效源可能持续显示成功并更新 `lastFetch` |
| 条目全部无效/过期 | `prepare` 静默丢弃，成功计数仍可能增加 | source health false-green，运营看不到“抓到了但没有可用内容” |
| purge/rescore/AI/revalidate 失败 | 周期捕获异常后仍返回普通 report | 调度器/监控误以为完整周期成功 |
| 文章相关查询失败 | `/a/[id]` 直接失败 | 一条辅助查询拖垮整篇阅读页 |
| 搜索少于 2 字或 0 结果 | 复用“抓取器预热”通用空状态 | 用户不知道搜索范围、输入要求和下一步 |
| 外部 feed 大字段 | parser/body 有总上限，但字段没有统一上限 | DB、JSON、DOM 和 LLM prompt 成本可被单字段放大 |
| Ask 并发 cache miss（基线） | 多实例同时 reserve/provider | 重复模型调用和额度消耗；本轮已用短时跨进程租约合并 |

## 3. 共识与分歧

### 3.1 三组 Agent 的共识（本轮 P1）

- **先修事实层，再扩展功能。** 缓存、source health、周期状态和输入边界是所有上层体验的基础。
- **明确数据范围。** 在搜索和热榜文案中直接说明“实时速闻”与“Hot AI 最近 14 天入库语料”的区别。
- **失败要可见且可分类。** 空响应、全量过期、全量非法、部分持久化失败不能都算成功，也不能把单一低频源简单等同于系统不可用。
- **阅读闭环应优先于新页面。** Digest 站内回链、文章页辅助查询隔离、搜索空状态的收益高于现在就做主题页或源管理后台。
- **Ask 引用需要改协议。** 仅靠前端正则解析 `[n]` 不能建立可信来源映射；本轮已传递受校验的 corpus metadata，并把引用号映射到站内文章。

### 3.2 有意保留的分歧与决策

| 议题 | 观点 | 决策 |
| --- | --- | --- |
| stale source 是否让 `/health` 变 503 | pipeline 线担心低频源造成误报；UX 线希望运营看到真实退化 | 本轮保持“服务可用”与“管道健康”分离：`ready` 代表服务可用，warnings/status 表示退化；不因单源 stale 直接 503 |
| 全量旧条目是否自动禁用源 | 可靠性线希望避免无效循环；pipeline 线提醒低频源会误伤 | 增加丢弃分类；全量过期可记录 degraded 但不自动禁用，全量非法/空响应才进入失败计数 |
| 主题页/源管理/首页 SSR snapshot | 都有价值，但会扩大数据边界和回归面 | 延后到第二阶段，先完成搜索语义、缓存和数据健康 |

## 4. 优先级方案

### P0：必须先做

1. stale-if-error 使用不可滑动的原始成功时间，并加回归测试。
2. 所有外部 feed 字段和 AI 输入设置长度上限，避免单字段放大成本。
3. 周期 report 显式携带 `status` 与 `errors`；revalidate 非 2xx 算失败。
4. source health 成功时清理 `lastErrorAt`，空响应/全量非法的状态可观测。
5. 无启用来源时周期标记 `degraded`，不能把“全部来源已停用”写成成功。

### P1：本轮实现

1. 搜索页显示语料范围、最短输入提示和“无结果”下一步；热榜标题改为准确的 14 天语义。
2. 文章页把 related 查询隔离为可失败的辅助步骤。
3. Digest bullet 保留/推导 Article ID，优先渲染站内详情链接，同时保留安全的外部来源链接。
4. 持久化统计增加 accepted/discarded 分类，为 source health 和运营排障提供证据。
5. Ask 相同问题的跨进程 cache miss 使用协调租约单飞；答案保存来源快照，SSE 与前端引用可点击且不会因热榜重排错位。
6. Ask 流式调用期间续租单飞记录，且过期 Ask 租约纳入周期清理，避免慢请求重复计费和协调表无界增长。
7. 分类、来源、博客、OPML 与 sitemap 对数据库不可用提供可恢复降级；各抓取适配器统一条数上限，模型提示输入做转义和长度封顶。

### P2：后续阶段（本轮不扩大）

- 首页 no-JS 首屏快照和分段流式 catalog 响应。
- 快照型源的真实发布时间字段（当前 GitHub Trending/中文列表只能以观测时间近似）。
- 旧租约 worker 的写入 fencing、FTS/分页、主题页、源管理与逐源重试 UI、SimHash、Webhook。
- Source 健康计数与停用目前是两个条件写入；若极端并发/数据库故障导致第二次写入未确认，系统会标记退化并在下一周期重试，生产上仍可升级为单条原子 SQL。
- 生产迁移、凭据轮换、备份恢复、HSTS/Nginx/原子发布和监控告警。

## 5. 本轮验收标准

- 缓存单元测试证明：首次 stale 失败后，即使每两分钟重试，超过 45 分钟仍不会继续返回旧 feed。
- parser/store 测试证明：超长标题、摘要、作者被截断，且不会改变 URL 安全策略。
- fetcher 类型与测试证明：`accepted/discarded` 可被 report 汇总；关键阶段错误进入 `errors`，周期状态为 `degraded`。
- 搜索和热榜文案在中英文下都准确说明范围；q<2 与零结果各有独立空状态。
- Digest 新旧数据均可安全渲染；可匹配 Article ID 时出现 `/a/{id}` 站内链接，无法匹配时仍保留外链。
- 文章 related 查询失败不会阻止正文、摘要和原文入口呈现。
- Ask SSE 会传递与答案绑定的来源快照；`[n]` 引用可打开对应站内文章，旧缓存没有快照时仍能正常显示答案。
- `pnpm test`、`pnpm typecheck`、`pnpm lint` 完成；`pnpm build` 若受本地 PostgreSQL 缺失阻断，须明确记录而不是伪装通过。

## 6. 本轮实现与验证记录

主要改动覆盖 `feed-cache`、远程 feed/parser、fetcher `store/cycle/sourceHealth`、AI prompt/digest、Ask SSE、Digest/Search/Article UX，以及数据库协调租约迁移。新增纯函数/回归测试覆盖 stale 窗口、字段上限、丢弃分类、内容健康、Digest/Ask 来源回链和 prompt 分隔符转义。

本地验证结果：`corepack pnpm test`（34 个文件通过，154 个测试通过；5 个数据库集成文件、15 个集成用例因未设置 `RUN_DB_TESTS` 跳过）、`corepack pnpm typecheck`、`corepack pnpm lint`、`corepack pnpm build:runtime`、`corepack pnpm smoke:dist` 和完整 `corepack pnpm build` 均退出成功。Web build 使用了明确的数据库降级路径；本机 `localhost:5432` 未运行，因此没有声称数据库集成或真实源抓取已验证。

## 7. 生产前仍需人工执行

代码修复不能替代部署与运营动作：生产数据库迁移和回滚演练、AI/RSS 凭据轮换、备份恢复演练、反向代理 TLS/HSTS、PM2/容器滚动发布、告警阈值和逐源健康看板仍需要目标环境权限。本报告把这些列为发布门槛，不把它们混入本地代码“已完成”清单。
