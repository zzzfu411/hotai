## 1. 执行摘要

### 1.1 最终结论

这个仓库不是空壳。首页速闻、数据库热榜、每日简报、Ask SSE、站内阅读、自定义订阅、RSS/JSON Feed、源抓取、去重、评分和 AI enrichment 都有实质代码，主要页面和 API 也能追踪到真实数据链路。

但当前实现更接近“有限流量 Beta”，不应在完成安全止血和可靠性修复前被视为可直接公开扩容的生产系统。

最关键的判断如下：

- 立即止血项：示例环境变量默认预填第三方 AI relay，且非空占位 token 会误启 AI。保留占位 token 时，内容会被发往第三方但真实 API key 因 token 优先不会发送；若用户为官方直连清空 token、填写真实 API key，却忘记清空第三方 base URL，则真实 key、文章内容和 Ask 问题可能一起发送到第三方。
- 安全边界不闭合：Feed、数据库文章、crossPosts 和 Digest URL 没有统一限制为 HTTP/HTTPS；已复现 javascript: URL 原样进入可点击链接，具备潜在点击型 XSS/钓鱼风险，但尚未做真实浏览器点击副作用验证。
- 成本保护不可靠：限流信任客户端可伪造的 X-Forwarded-For；Ask 并发可越过额度，浏览器断开不会取消上游 LLM；Digest 禁用开关不能阻止 Web 首访生成。
- 数据承诺不成立：“每篇文章可靠完成 AI”“14 天硬保留”“HN AI filter”“今日热榜”“全文搜索”等声明与源码存在实质差异。
- 工程门禁存在假绿：89 个现有单元测试通过，根 typecheck 也通过，但 packages/db 被漏检且独立 typecheck 失败。
- 生产产物不完整：fetcher 虽能生成 dist，却仍依赖指向 TypeScript 源码的 workspace 包；部署指定的 Node 20 不能直接运行该 dist。
- 首次部署流程有阻断和安全错误：TLS 配置先启用无证书的 443，再运行 certbot；生产文档使用 migrate:dev；secret 生成示例会变成字面量；固定弱数据库口令、非原子发布和不可验证备份也没有闭环。

### 1.2 风险评级

## 3. 真实架构与数据流

### 3.1 技术栈

- pnpm 9.12 monorepo。
- apps/web：Next.js 14.2.15、React 18.3.1、App Router。
- apps/fetcher：Node worker、node-cron、RSS/API/scrape 抓取。
- packages/db：Prisma 5.19.1、PostgreSQL。
- packages/ai：Anthropic SDK 0.32.1，可指向兼容 relay。

### 3.2 两条独立内容链路

速闻链路：

    Browser
      -> POST /api/catalog/pull
      -> allowlisted catalog source
      -> fetchPublic / feed cache
      -> RSS / Atom / JSON Feed parser
      -> client-side merge and sort
      -> 首页时间线

该链路不写 Article 表。首页真实新闻只在 hydration 后从客户端请求，初始 HTML 不包含文章列表。

Hot AI 链路：

    fetcher startup / cron
      -> purge
      -> fetch enabled Source
      -> normalize / dedupe / persist
      -> rescore
      -> AI enrichment
      -> Daily Digest
      -> POST revalidate
      -> Web 通过 Prisma 查询 Article / Digest

这条链路写入 Article、Source 健康字段和 Digest。

### 3.3 Web 并非完全只读

README.md:50-52 的“fetcher 是唯一写入者；web 只读”不成立：

- apps/web/lib/digest.ts:55-73 会在首访时 upsert Digest。
- apps/web/app/api/ask/route.ts:51-57,118-125 会读取、更新和 upsert AskCache。

## 6. P0：立即止血

### P0-01 示例配置默认指向第三方 AI relay，可能泄露真实凭据和内容

证据：

- .env.example:53 将 ANTHROPIC_AUTH_TOKEN 设置为非空占位值 "<your-relay-key>"。
- .env.example:64 默认设置 ANTHROPIC_BASE_URL=https://2c2ch1u11-share-api-0.hf.space。
- .env.example:71-72 默认覆盖为第三方模型 ID。
- packages/ai/src/client.ts:15-18 只要 token 或 API key 任一非空就令 AI_ENABLED=true。
- packages/ai/src/client.ts:37-44 会将鉴权和请求发送到配置的 base URL，并且 auth token 优先于 API key。
- README.md:65-66 指示用户复制 .env.example，再“可选”填写 Anthropic 凭据。

真实机制：

1. 原样复制示例后，占位 token 被当成已配置，AI 实际进入启用状态。
2. 用户若只填写真实 ANTHROPIC_API_KEY，却保留非空占位 token，代码会令 token 优先并把 apiKey 设为 null：真实 API key 不会发送，但文章内容和 Ask 请求仍会携带占位 Bearer token 发往第三方，随后大概率失败。
3. 用户若按“官方直连”意图清空 token、填写真实 API key，却忘记清空预填 ANTHROPIC_BASE_URL，请求仍指向第三方；这时真实 API key、文章标题/摘要/URL、Digest 候选和用户问题都可能被交给该端点。
4. 请求失败后，当前 enrichment 逻辑还会把文章永久标记 skipped，造成二次数据损失。

影响：

- 这是配置供应链层面的凭据和内容泄露路径。
- 仓库中没有证据证明已经发生泄露；重点审计对象是“已清空 auth token、填入真实 API key、但仍保留第三方 base URL”的环境。

立即动作：

1. 将示例中的 ANTHROPIC_AUTH_TOKEN、ANTHROPIC_API_KEY、ANTHROPIC_BASE_URL、LLM_MODEL_FAST、LLM_MODEL_SMART 全部改为空值。
2. 官方直连必须依赖 SDK 默认端点，不在模板中预填任何第三方域名。
3. 启动时 trim 值并拒绝 <...>、changeme、example 等占位符。
4. 非官方域名必须同时设置显式确认开关，例如 ALLOW_THIRD_PARTY_AI=true。
5. 同时配置 token 和 API key 时 fail-fast，不允许静默优先级。
6. 审计所有部署环境；凡曾清空 auth token、填写真实 API key 且保留该第三方 base URL，立即轮换 key，并检查供应商访问日志和异常用量。

验收标准：

- 原样复制 .env.example 后 AI_ENABLED=false，且没有 AI 出站请求。
- 只填写官方 API key 时，请求目标只能是官方 Anthropic 端点。
- 未显式确认时，非官方 base URL 导致启动失败。
- 占位符、纯空格和双凭据均有自动化测试。

## 7. P1：发布阻断与高风险缺陷

### P1-01 危险协议 URL 可进入可点击链接，存在潜在点击型 XSS/钓鱼风险

证据：

- apps/web/lib/parse-remote-feed.ts:112-118 的 absUrl 使用 new URL，但不检查 protocol。
- JSON Feed 路径在 153-157 接受 url、external_url，甚至把 opaque id 当作 URL。
- RSS/Atom 路径在 195-198 使用同一逻辑。
- apps/web/components/SubscribeClient.tsx:581-588 将 item.url 直接渲染为 a href。
- apps/web/components/ArticleCard.tsx:106-114、apps/web/app/a/[id]/page.tsx:72-76,125-133 直接渲染 Article 和 crossPosts URL。
- packages/ai/src/digest.ts:85-103 接受任意字符串 URL，apps/web/app/digest/page.tsx:43-63 直接渲染。
- apps/fetcher/src/dedupe.ts:22-43 的 normalizeUrl 同样接受 javascript: 和 data:。
- apps/fetcher/src/sources/rss.ts:24-38 直接接受 link/guid；store.ts:112-137,220-236 未经 scheme 校验便 normalize/hash/落库。
- apps/fetcher/src/store.ts:146-152,183-205 还可把同类 URL 写入 crossPosts。
- 已实际复现 javascript:alert(1) 从 JSON Feed 原样进入可点击 href。

其中 Web JSON Feed 到 href 为 A 级运行复现；fetcher 到 Article/crossPosts 为 B 级源码调用链证据，尚未在真实数据库中插入恶意行。

影响：

- 恶意或被入侵的 Feed、错误数据库内容、LLM 幻觉或 prompt injection 均可产生危险链接。
- 用户点击后可能触发浏览器对危险协议的执行或被引向 data/file/vbscript 等非预期协议；具体脚本执行上下文需要真实浏览器回归确定，不能仅凭 SSR 输出断言已经执行。

修复要求：

- 在共享包建立 parseExternalHttpUrl，只允许无 username/password 的 http: 和 https:。
- 在 Feed 解析、fetcher 入库、crossPosts 解析、Digest schema 四个入口拒绝危险 scheme。
- 所有出站渲染 sink 再做一次 fail-closed 校验；无效值显示为不可点击文本。
- JSON Feed 没有 url/external_url 时，不把任意 id 自动变成链接。
- 对已有数据库执行只读审计，先将不合规 URL 标记/隔离，再决定修复或删除。

验收标准：

- javascript:、data:、vbscript:、file:、带 credentials 的 URL 全部被拒绝。
- RSS、JSON Feed、Article、crossPosts、Digest 各有单元和浏览器回归测试。
- Playwright 点击恶意条目时不能执行脚本，页面 origin 不发生脚本副作用。

### P1-02 公共限流可被伪造 X-Forwarded-For 绕过，内存键也无硬上限

证据：

- apps/web/lib/ask-guard.ts:44-47 无条件使用 X-Forwarded-For 的第一项。
- deploy/nginx.conf:39-40 使用 $proxy_add_x_forwarded_for，会保留客户端自带头并把真实 IP 追加到末尾。
- Ask、catalog、feed proxy、readability 都复用该 clientIp。
- apps/web/lib/ip-rate-limit.ts:34-48 和 ask-guard.ts:65-69 达到 2048 后只清理过期键；若全部未过期，仍继续插入。
- apps/web/lib/ssrf.ts:231-263 的 DNS memo 达到 512 后也只删除过期项，没有硬淘汰。

影响：

- 攻击者每次更换伪造首个 XFF 即可绕过请求数和 AI 成本保护。
- 大量伪造 IP 可令 Map 在窗口内持续增长，形成内存压力。
- 伪造 XFF 配合大量唯一子域，可同时膨胀限流 Map 和 DNS memo。
- 多个 PM2 实例时，各实例计数还会进一步分裂。

修复要求：

- 单层 Nginx 部署直接覆盖 X-Forwarded-For 为 $remote_addr，应用优先读取可信的 X-Real-IP。
- 多层代理必须配置可信代理 CIDR，并从右向左剥离可信 hop。
- AI 和公共 fetch 限流迁移到 Redis 或 PostgreSQL 原子计数；所有内存 limiter/cache 至少增加全局并发、总键硬上限和确定性淘汰。
- 对请求体在 req.json 前做 Content-Length 和流式上限。

验收标准：

- 客户端自带任意 XFF 不改变最终识别 IP。
- 同一真实 IP 超限后稳定返回 429。
- 10 万个伪造 IP 不会导致键数越过配置硬上限。
- 大量唯一子域不能令 DNS memo 越过配置硬上限。
- 双 Web 实例下限流结果一致。

### P1-03 标准 NAT64 表示实际未被识别，并默认放行 198.18.0.0/15 DNS 结果

证据：

- apps/web/lib/ssrf.ts:98-117 通过字符串正则识别 mapped IPv4/NAT64；现有 NAT64 正则只匹配非标准短形式，对合法的 64:ff9b::7f00:1 和完整八段表示实际无效。
- isBlockedResolvedAddress 在 92-95 将 198.18.0.0/15 作为 fake-IP DNS answer 明确放行。
- resolvePublicHostname 在 244-263 会将选中的地址 pin 给连接。
- 现有测试固定了 198.18 DNS 放行行为。

影响：

- 在 NAT64、TUN、Clash 或特殊本地网络中，恶意域名可能通过地址表示差异或 fake-IP 路由触达不应访问的本地目标。
- 该项依赖部署网络，属于 C 级条件风险，但一旦命中即跨越 SSRF 安全边界。

修复要求：

- 使用成熟的 128 位 IP 解析库覆盖 IPv4-mapped、64:ff9b::/96、64:ff9b:1::/48 及所有特殊网段。
- 198.18.0.0/15 默认拒绝；如必须支持 Clash fake-IP，使用显式部署开关和受信 DNS 约束。
- 保留现有“检查全部 DNS 答案、任一私网即拒绝”的正确策略，并让改进后的 NAT64/特殊网段判断覆盖每一个答案。

验收标准：

- NAT64 映射的 127.0.0.1、10/8、169.254.169.254 全部拒绝。
- 198.18.0.0/15 默认拒绝。
- 重定向每一跳继续校验并 DNS pin。

### P1-04 AI 瞬时失败会被永久标记 skipped

证据：

- apps/fetcher/src/enrich.ts:74-93 对整批失败会降级单篇。
- packages/ai/src/enrich.ts:99-115,127-164 将超时、429、认证、解析和供应商错误统一转成 null。
- apps/fetcher/src/enrich.ts:106-115 对任意 null 写 aiAnalyzedAt=now 和 aiModel=skipped。
- 后续查询只选择 aiAnalyzedAt:null，见 apps/fetcher/src/enrich.ts:31-34。

影响：

- 短暂网络故障、限流或 relay 错误会永久失去摘要、主题和 importance。
- 批次中单个无效元素不会再次单篇重试。
- 修改模型或 prompt 后没有版本化重跑机制。
- “每篇新文章都经过一次 LLM”真实含义只是“最多尝试一次”。
- pending 查询永远按 score 降序取固定 top-N，没有 aging 或 oldest 配额；当持续入库速度超过处理能力时，低分文章可能直到 retention 删除都从未被尝试。

修复要求：

- 增加 aiStatus、aiAttempts、aiNextAttemptAt、aiLastError、aiPromptVersion、aiLeaseUntil。
- 只有 success 才设置 aiAnalyzedAt。
- 429、5xx、timeout 指数退避；结构永久无效达到上限后才进入 failed。
- 批次内单个 null 也应进入单篇 fallback。
- 提供 requeue 运维命令，可按 status、模型或 prompt 版本重跑。
- 调度中加入年龄权重或为最老 pending 预留配额，并暴露 backlog 数量、最老 pending 年龄和处理 SLO。

验收标准：

- 模拟首次 429 后文章仍可重试，下一周期成功。
- failed、pending、leased、success 可独立统计。
- 模型或 prompt 版本改变后可安全重入队，且不会重复并发消费。
- 在持续高流量 fixture 下，所有符合条件的文章都能在保留期和定义的 backlog SLO 内至少被处理一次。

### P1-05 Digest 结构与 URL 只靠 prompt，没有真正强制

证据：

- packages/ai/src/digest.ts:37-50 的 prompt 要求恰好 4 条、URL 来自输入。
- 实际转换在 85-103 允许 0 到 6 条、每条 0 到 3 个任意字符串 URL。
- 空对象可被转换成空 headline、空 overview、空 bullets。
- apps/fetcher/src/digest.ts:52-72 和 apps/web/lib/digest.ts:55-73 不做二次校验便写库。
- apps/web/app/digest/page.tsx:45-61 将 URL 直接渲染为外链。

影响：

- Feed 内容中的 prompt injection 或模型幻觉可产生恶意、钓鱼或无关 URL。
- “恰好四条强新闻”只是模型愿望，不是系统约束。
- 损坏 JSON 还可能在读取端 .map 时令页面 500。

修复要求：

- 使用 Zod 或 JSON Schema，要求 headline/overview 非空且有长度上限，bullets 恰好 4 条。
- 每条 title/takeaway 非空，URL 数量和长度受限。
- URL 必须属于本次输入 Article URL 集合，并再次通过 HTTP/HTTPS 校验。
- 校验失败时重试或保留旧 Digest，不写入坏数据。
- 读取数据库 JSON 时也必须 schema.parse，而不是类型断言。

验收标准：

- 第五条、空数组、空字段、伪造 URL、javascript:、缺字段全部被拒绝。
- 成功记录恒有 4 条，所有 URL 均能映射到输入 Article。

### P1-06 Ask 和 Digest 的成本阀不能覆盖断开、并发和禁用场景

证据：

- apps/web/app/api/ask/route.ts:81-130 创建 LLM stream，但没有传递 req.signal。
- 浏览器 AskBox abort 后，上游仍可能继续生成和计费。
- quota 在调用前只检查，流结束后才在 114-117 增加；并发请求可同时越过上限。
- 失败或断开产生的 token 不计额度。
- ask-guard.ts:38-42,76-93 将日额度保存在单进程内存；进程重启即清零，多实例分别计数。
- .env.example:87-88 声称 AI_DIGEST_ENABLED=false 可禁用 Digest。
- apps/web/lib/digest.ts:36-55 忽略该变量，首访仍调用 generateDigest 并写库。
- PulseRail.tsx:75-77 在 /hot 无条件渲染 AskBox，而 /api/ask 在 AI 未配置时固定返回 503。

影响：

- 匿名用户可通过并发和断开放大 AI 成本。
- 重启进程或将 Web 扩为多实例会使日额度阀失去全局意义。
- 配置管理员以为已关闭 Digest，但 Web 仍可产生调用。
- AI 未配置时，用户仍会看到必然失败的 Ask 表单。
- 保存 Digest 失败后没有冷却，后续访问者可能重复支付相同调用。

修复要求：

- 将 req.signal 传给 SDK；ReadableStream 实现 cancel 并停止上游。
- 使用 Redis/PostgreSQL 等持久共享存储，在请求前跨实例原子预留最大 token，结束后结算；失败消费也记账。
- 增加全站 LLM 并发上限和每模型成本指标。
- Web 与 fetcher 读取同一份 AI_DIGEST_ENABLED schema。
- Digest 保存失败时保留短期生成结果并设置 retry cooldown。
- Web 服务端将 AI capability 明确传给 /hot；未配置时隐藏 Ask 或显示不可提交说明。

验收标准：

- 客户端断开后上游请求在限定时间内 abort。
- 并发压力下消耗不超过上限加一个已预留请求的容忍值。
- 进程重启和双实例下，日额度使用量保持一致且不会清零。
- AI_DIGEST_ENABLED=false 时任何页面/API 都不会调用 generateDigest。
- AI 未配置时 /hot 不出现可提交且必然返回 503 的 Ask 表单。

### P1-07 逐条持久化错误被吞，Source 仍被记录成功

证据：

- apps/fetcher/src/store.ts:85-109 捕获每条异常，只累加 stats.failed。
- apps/fetcher/src/cycle.ts:94-103 不检查 failed，仍 sources.ok++ 并调用 recordFetchSuccess。

影响：

- 唯一冲突、非法日期、JSON 或数据库错误可造成静默数据丢失。
- 即使整批 Article 全部失败，Source 仍会清零连续失败计数。
- 监控、日志和自动停用都得到错误健康信号。

修复要求：

- 将 fetch、validation、persist 三类状态分开。
- 全部持久化失败必须抛错；部分失败标记 degraded，不能清零健康状态。
- 并发唯一冲突应回读并 merge，而不是直接记失败。
- report 明确 attempted、invalid、created、refreshed、merged、failed。

验收标准：

- 模拟全部 create 失败时 Source 不得显示成功。
- 部分失败能准确记录原因和数量。
- 双 worker 写相同 URL 后只有一行，双方都不误报静默丢失。

### P1-08 “14 天硬保留”和时间新鲜度约束不成立

证据：

- apps/fetcher/src/cycle.ts:45-52 在抓取前 purge。
- store.ts:112-139,212-238 在后续插入前没有 cutoff。
- RSS/Hugging Face 日期没有统一有限值和未来上界校验。
- apps/fetcher/src/purge.ts:9-18 只按 publishedAt 删除。
- scoring.ts:47-51 将未来时间 age 强制为 0。
- Web 的 getTopArticles/getFeedArticles 没有 14 天 cutoff。
- Digest 查询没有 tomorrow 上界。

影响：

- 低频 Feed 中的旧条目会在 purge 后重新插入，至少存在到下周期。
- fetcher 停止或 purge 失败时，数据库和 Web 都不再保证 14 天。
- 未来时间文章长期保持最高新鲜度，并可进入今日 Digest。

修复要求：

- 入口统一校验 Date.getTime、cutoff 和 now + 容忍窗口。
- 持久化前拒绝过旧或异常未来时间；cycle 末尾可再做防御性 purge。

- Digest 使用 [today, tomorrow)。
- 区分 publishedAt、firstSeenAt、lastSeenAt；Trending 使用 lastSeenAt。

验收标准：

- cycle 完成后不存在 cutoff 之前或未来容忍上界之后的 Article。
- 覆盖 cutoff 前后 1ms、Invalid Date、未来 1 天测试。
- fetcher 停止时 Web 查询仍不返回过期文章。

### P1-09 数值和 cron 配置没有范围校验，可清表或停掉流水线

### P1-10 Fetcher HTTP 超时不覆盖响应正文，且正文无大小上限

验收标准：

- 慢正文必须在 FETCH_TIMEOUT_MS 加容忍值内中止。
- 超过上限的 Content-Length 和 chunked body 均停止读取。
- 单源慢流不应阻止下一周期调度和健康告警。

### P1-11 同 URL 内容更新后，titleHash、元数据和 AI 结果会永久陈旧

- 根 typecheck 包含 db 并全部通过。
- release 中不存在运行时从 packages/*/src 加载 .ts 的路径。

### P1-13 首次部署的 secret、migration 和 TLS 流程存在实质错误

证据：

- deploy/README.md:74-80 将 REVALIDATE_SECRET="$(openssl rand -hex 32)" 写成 .env 示例。
- 自制 env loader 只切分文本，不执行 shell 命令替换；secret 会成为可预测字面量。
- revalidate API 接受调用方提供的任意 paths。
- deploy/README.md:102-110 和 README.md:68-71 将生产首次迁移引向 migrate:dev。
- 仓库已有 migrations，packages/db/package.json:9 已提供 migrate deploy。
- deploy/nginx.conf:16-22 直接启用 443 ssl，但没有证书路径。
- deploy/setup.sh:61-62 要求先 nginx -t/reload，再运行 certbot。

影响：

- 可预测 secret 可被用于反复失效任意路径缓存。
- migrate:dev 可能要求 shadow DB、制造生产独有 migration 和 schema 漂移。
- 全新机器可能因无证书导致 nginx -t 失败，certbot 又无法继续。

修复要求：

- 在 shell 中先生成随机值，再安全写入权限 600 的 .env；启动时校验熵和占位符。
- revalidate 只接受固定路径 allowlist 和有限数量。
- 生产只运行 prisma migrate deploy。
- 提供 HTTP-only bootstrap 配置；证书签发后再启用 TLS server block。

验收标准：

- 全新 Ubuntu/Debian 主机每一步 nginx -t 都通过。
- 无 CREATEDB 权限的生产角色可完成全部已提交 migration。
- 非 allowlist revalidate path 返回 4xx。
- certbot renew --dry-run 通过。

### P1-14 发布、PM2 和备份流程不能提供声称的零停机与可恢复性

证据：

- ecosystem.config.js 的 Web/fetcher 都是单实例 fork。
- deploy/README.md:202-210 在当前目录直接 pull、migrate、覆盖 .next，再 pm2 reload all，并声称零停机。
- fetcher 没有 SIGTERM/SIGINT drain。
- deploy/setup.sh:33-41 创建固定弱口令 hotai/hotai。
- .env 权限没有自动设置。
- 备份 cron 未可靠创建目录、未明确 TCP host/认证、无校验和、异地存储和恢复演练。

影响：

- 单实例 fork reload 不能保证 Web 零停机。
- 原地构建会改写正在运行进程使用的文件。
- schema 先变更时旧代码可能立刻不兼容。
- 抓取/写库/AI 任务可在中途被杀。
- 备份任务可能静默失败，即使生成文件也没有恢复证据。

修复要求：

- 使用版本化 release 目录，构建完成后原子切换 current symlink。
- 数据库迁移遵循 expand-contract。
- Web 使用至少双实例 cluster 或外部负载均衡。
- fetcher 支持 graceful drain，仅定向重启 hotai-web/hotai-fetcher。
- 安装时生成随机 DB 密码，使用安全 secret 文件。
- 备份显式指定 host、认证、目录、校验、加密和异地存储，并提供恢复脚本。

验收标准：

- 在预先定义的压测窗口内（例如 10 分钟、20 RPS），没有由部署切换引入的 5xx 或连接中断；构建失败不影响旧 release。
- 运行中的 fetch cycle 可完成或安全中止。
- 无关 PM2 应用不被操作。
- 每月在空数据库完成恢复演练，并通过 prisma migrate status、关键表行数/约束/校验和、应用读写 smoke 及定义的 RPO/RTO 验证；Prisma validate 只能作为 schema 文件语法检查，不能替代恢复验收。

## 8. P2：功能语义、可靠性与质量问题

### P2-01 Fetch cycle、AI claim 和 Source 健康只支持单实例

证据：

- apps/fetcher/src/index.ts:7-19 的 overlap guard 是进程内布尔值；--once 绕过该 guard。
- store 先批量查询再 create，跨进程存在 check-then-act 竞态。
- enrichment 查询 pending 后没有 lease/claim。
- Source.consecutiveFails 基于旧对象计算，非原子 increment。

影响：PM2 重复实例、手工 fetch:once 与 cron 重叠时，可能重复 AI 成本、重复 create、丢失失败递增和产生 canonical 竞态。

修复与验收：

- 用 PostgreSQL advisory lock 锁整个 cycle。
- AI 使用 lease/status 或 FOR UPDATE SKIP LOCKED。
- Source 健康使用原子 increment 和 RETURNING。
- 同时启动两个 cycle，必须只有一个执行；每篇文章只调用一次 AI。

### P2-02 Enrichment 的“严格 JSON”实际非常宽松

证据：

- packages/ai/src/enrich.ts:75-97 只要求外层是对象。
- 空对象会变成空摘要、空 topics、importance=0 的成功结果。
- 数字/对象可能经 String 转成无意义文本。
- prompt 中摘要长度、3 到 5 topics、importance 范围没有强制。

修复与验收：

- 用运行时 schema 校验类型、非空、长度、topic 数量、去重和 importance 0 到 1。
- 空对象、数字摘要、超长内容、重复 topics 必须失败并进入可重试状态。

### P2-03 标题 canonical 和 crossPosts 来源统计不确定

证据：

- cycle 的 Source 查询无 orderBy，并按返回顺序逐源持久化。
- 当前 cycle 中先处理者成为 canonical，即使发布时间更晚或来源权重更低。
- crossPosts 只按 URL 去重，同一原文经不同来源报道只保留一个来源。
- normalizeTitle 未做 Unicode NFKC；测试名声称 width-insensitive，但没有覆盖全角 Latin。

修复与验收：

- cycle 内先聚合候选，再按“原始/官方源优先、最早发布时间、稳定 tie-breaker”选择 canonical。
- crossPost 唯一键改为 source slug + normalized URL；若未来迁移为 sourceId 外键，需同时定义 Source 删除后的历史保留策略。
- title 先 NFKC、去零宽字符。
- 打乱 Source 顺序多次运行，最终 canonical 必须一致。

### P2-04 不同来源信号量纲和 freshness 语义会扭曲排名

证据：

- Hugging Face 将累计 downloads 直接送入信号。
- scoring 对所有来源使用同一 log 压缩，但累计下载、HN points、GitHub stars 的含义和分布不同。
- AI importance 最大贡献默认 2.0，可能被大累计信号长期压过。
- Trending 首次观测可用当前时间，后续却继续按首次 publishedAt 衰减。

修复与验收：

- 按来源使用日增量、分位数或标准化分数。
- Trending snapshot 以 lastSeenAt 或独立 freshness 字段参与衰减。
- 建立跨来源排名黄金数据集，规定 top-N 的来源多样性和顺序容忍区间。

### P2-05 Source 健康状态会误报，自动停用后没有恢复闭环

证据：

- health update 失败后代码仍可能返回 disabled。
- success 清空 lastError，但不清理/区分 lastErrorAt。
- RSS/API 返回空数组会记成功，只有 scrape 空结果被视为失败。
- 自动停用后没有定期探测、告警或自动恢复。

修复与验收：

- 区分 healthy、degraded、failed、disabled、probing。
- 对预期非空来源设置连续空结果阈值。
- disabled 来源定期低频探测，恢复需达到连续成功门槛。
- DB health 写入失败必须进入 cycle report，不能声称已停用。

### P2-06 数据库缺少关键完整性约束和任务状态

证据：

- Source.type/lang/category、Article.lang/category/sentiment、weight、importance 多为无约束 String/Float。
- aiImportance 没有 0 到 1 CHECK。
- Digest.bullets 仅为 Json。
- Article 缺 updatedAt、lastSeenAt、contentHash；AI 缺 retry/status/version 字段。
- 部分 SQL 数组列与 Prisma required 类型的 nullability 不完全一致。

修复与验收：

- 使用 Prisma enum 或数据库 CHECK。
- 先审计/清理脏数据，再增加 NOT NULL 和范围约束。
- 原始 SQL 插入非法 category、importance=2、null required array 必须失败。
- Prisma 类型与数据库可空性一致。

### P2-07 Seed 不是事务化配置同步

证据：

- packages/db/src/seed.ts:1292-1350 逐条 upsert，无事务。
- 移除或改名的 Source 不会被 prune，旧源可能永久保留。
- Source update 保留 enabled，CuratedBlog update 却强制 enabled=true，所有权语义不一致。

修复与验收：

- seed 使用事务。
- 明确“代码管理字段”和“运维管理字段”。
- 提供显式 --prune 或将已移除项标为 disabled，默认不直接删除。
- 模拟中途失败后数据库必须全回滚。

### P2-08 首页是纯客户端时间线，核心内容无 JavaScript 不可用

证据：

- apps/web/app/page.tsx 虽 force-dynamic，但没有服务端读取内容。
- NookFeed.tsx 是 client component，新闻在 hydration 后 effect 中请求。
- 初始 HTML 不含文章链接，fetcher 对 / 的 revalidate 对数据没有实际作用。

影响：

- 无 JavaScript、弱设备、爬虫和网络抖动场景下首页核心产品为空。
- 首屏可见时间依赖额外 API waterfall。

修复与验收：

- 服务端并发加载默认 catalog，传 initialSnapshot 给 NookFeed。
- 使用服务端 Feed cache/短 ISR，客户端只刷新和应用 localStorage 个性化。
- curl / 必须能看到首批真实标题和链接；禁用 JavaScript仍可浏览。

### P2-09 “今日热榜”查询没有任何最大时间边界

证据：

- apps/web/lib/queries.ts:21-26 的 getTopArticles 没有当天起始条件。
- /hot 页面标题固定为“今日热榜”。
- 正常 purge 条件下结果通常接近配置的保留窗口；但 purge 可失败、fetcher 可停机且旧文可重插，因此源码层面可以返回任意久远 Article。

修复与验收：

- 产品二选一：查询改成 startOfUtcDay；或显式增加 N 天 cutoff，并把标题、metadata 和文档统一为“当前热榜/近 N 日热榜”。
- 固定时钟集成测试验证昨天高分文章是否符合选定语义。

### P2-10 编辑 OPML 导出 scrape/API 地址，导入后系统性失败

证据：

- apps/web/app/hotai.opml/route.ts:19-25 导出所有 enabled Source。
- seed 中 36kr-ai、infoq-cn-ai、github-trending、huggingface-trending、huggingface-papers 不是可订阅 Feed。
- /subscribe 提供“一键导入编辑目录”，会将这些地址存入自定义 Feed。

修复与验收：

- OPML 只导出 type=rss。
- 其他来源如有公开 Feed，应新增独立 feedUrl，而不是复用抓取/API URL。
- 自动下载 OPML 并逐个通过 parseRemoteFeed；所有 xmlUrl 必须可解析。

### P2-11 Search 不是全文搜索，结果数和状态也不真实

证据：

- apps/web/lib/queries.ts:62-82 使用 contains/ILIKE 与数组精确 has。
- 默认最多 60 条，没有相关度排序、搜索索引、分页或 total。
- UI 将返回数组长度当成总数。
- 单字符查询显示通用“抓取器预热”，而不是明确最小长度。

修复与验收：

- 使用 PostgreSQL tsvector + GIN，必要时增加 pg_trgm 处理短词/拼写。
- API/查询返回 items、total、nextCursor。
- 明确最小长度和相关度/最近/热度排序。
- 超过 60 条时能显示真实 total 并翻页，浏览器前进后退时输入与结果同步。

### P2-12 Ask 引用不可核验，缓存未绑定语料和模型

证据：

- prompt 要求输出 [3]，SSE 只发送 delta/done。
- AskBox 不知道编号对应的 Article URL。
- 缓存 key 只有规范化问题，不包含 corpus hash、模型、prompt 版本或日期。
- 语料变化后 24 小时内仍可返回旧编号和旧答案。

修复与验收：

- 首个 SSE 事件发送 citation snapshot，引用使用稳定 Article ID。
- 缓存 key 包含 question、corpus hash、model、prompt version。
- 每个引用可点击并指向当次回答使用的文章；语料变化后缓存失效。
- EOF 前未收到 done 时 UI 显示“回答中断”，不能把部分文本当成功。

### P2-13 Digest 页面、API 和错误语义不一致

证据：

- 页面会首访生成，/api/digest 只读现有记录。
- digest/page.tsx 将 DB、LLM 和保存错误全部吞成 null。
- DigestHeader 在 AI 开启时统一提示“至少需要 5 篇”，即使真实原因是 DB 或 provider 故障。
- 数据库 bullets 只做类型断言，坏 JSON 可在 .map 时令页面崩溃。
- Digest.lang 字段存在，但 date 单列 unique，实际只有一套单语字段。

修复与验收：

- 明确唯一服务层，让页面和 API 共享读取/生成策略。
- 运行时 schema 校验数据库 JSON。
- 区分 insufficient-data、AI-disabled、provider-error、DB-error。
- 要么删除 lang，要么迁移为 date + lang 联合唯一并真正生成多语言记录。

### P2-14 Feed 与 Readability 缓存的失败语义不闭合

证据：

- stale-if-error 返回旧数据后没有记录短失败 TTL，后续请求可持续重打坏上游。
- 负缓存会丢失 blocked/unrecognized 等原始错误类型。
- Readability 在缓存查询前限流，缓存命中也消耗冷 fetch 配额。

修复与验收：

- 缓存保存 errorKind、retryAt、staleFeed。
- 失败 TTL 内不重复访问上游，且错误类型稳定。
- Readability 先安全规范化 URL 和查成功缓存，再对真正冷请求限流。
- 坏源在两分钟窗口只访问上游一次；缓存命中不增加 cold-fetch 计数。

### P2-15 缺少 App Router error boundary 和稳定 API 错误契约

证据：

- 仓库没有 app/error.tsx 或 global-error.tsx。
- search、category、source、article、blogs、feeds、OPML、sitemap 的 DB 异常多会进入 Next 通用错误页。
- /hot 的异常降级可能在 ISR 再生成时把临时空页面缓存为成功结果。

修复与验收：

- 增加全局和高价值路由级 error/loading boundary。
- API 返回统一 JSON error code、message、requestId。
- ISR 再生成失败时保留 stale 页面。
- 模拟 DB 断开，页面显示品牌化 503/重试入口，API schema 稳定。

### P2-16 “稍后读 / 已读”没有消费端

证据：

- Reader 提供按钮，reading-flags.ts 只写 localStorage。
- getArticlesByIds 已存在但未使用。
- 没有 saved 页面、过滤器或导航入口；已读状态不影响卡片。

修复与验收：

- 增加 /saved 或 /hot?view=later/read。
- 受限批量查询 ID，过期/不存在 ID 自动清理。
- 标记后用户能从导航重新找到；刷新和跨页面状态一致。

### P2-17 内置 catalog source toggle 只有读取逻辑，没有可达 UI

证据：

- NookFeed.tsx:48,84-96 读取 hotai.nook.enabled。
- 仓库没有写入该 key 的 UI。
- geekpark、wired、lobsters 默认关闭且没有普通用户入口。
- 存储空数组会被恢复成默认值，不能真正关闭全部源。

修复与验收：

- 增加 catalog 管理界面，展示全部 allowlisted 源及健康状态。
- 允许空 selection，并跨刷新持久化。
- 每个 catalog source 都可通过 UI 到达。

### P2-18 Juya 解析对坏日期和相对资源不健壮

证据：

- apps/web/lib/juya.ts 对未知 pubDate 直接 toISOString，非法日期可抛错。
- sanitizeJuyaHtml 不基于原文 URL 重写相对 href/src。
- 当前 DOMPurify 配置没有禁止 style 属性；最小运行验证会保留 position:fixed、inset:0、z-index:999 等内联 CSS。
- 页面没有使用 issue.url，只链接站点首页。

影响：

- 被入侵或恶意的 Juya Feed 虽不能直接注入脚本，但可用全屏覆盖制造点击劫持式钓鱼，并可能通过外部 CSS 资源行为扩大跟踪面。

修复与验收：

- 安全日期解析，单条坏数据只跳过该条。
- 净化前后将相对链接和图片转成基于 item URL 的绝对地址。
- 默认使用 DOMPurify FORBID_ATTR: ["style"]；若业务确需样式，必须使用可靠 CSS sanitizer 和严格属性/值 allowlist。
- 增加“本期原文”。
- 一条坏日期不影响其余 issue。
- 恶意 position:fixed/inset/z-index 样式不能覆盖站点 UI。

### P2-19 RSS 2.0 输出和文档描述不完全合规

证据：

- feed.xml route 输出 source 文本，但 RSS 2.0 的 source 应带必需 url 属性。
- README 声称 description 使用 AI 摘要，实际会回退 raw summary。

修复与验收：

- 添加合法 source url 属性或删除该元素。
- 文档改为“优先 AI 摘要”。
- RSS XML 通过自动 schema/validator 测试。

### P2-20 自定义订阅的客户端验证与服务端规则不一致

证据：

- local-sources.ts 接受带 credentials、私网 IP 和超长 URL，服务端随后会拒绝。
- saveCustomSources 吞 localStorage 写入错误。
- UI 即使持久化失败仍可能显示“已添加”。

修复与验收：

- 共享同步 URL 语法规则；服务端继续做最终 SSRF 校验。
- save 返回明确成功/失败。
- 模拟 storage quota/private mode 错误时不显示成功，刷新后状态一致。

### P2-21 Web 缺少基础安全头、路由请求体上限和完整键盘焦点

证据：

- next.config.mjs 未配置 CSP、X-Content-Type-Options、Referrer-Policy、Permissions-Policy 和 frame policy。
- Nginx 全站 client_max_body_size 为 10 MB，Ask/readability/catalog 在解析 JSON 前没有更小路由限制。
- proxy/feed 为 GET，第三方网页可触发服务器出站请求。
- globals.css 的通用 focus 样式被后续 outline:none 覆盖。

修复与验收：

- 增加基于 nonce/hash 的 CSP 和常用安全响应头。
- 各 API 设置 8 到 32 KB 请求体上限，超限返回 413。
- proxy 改 POST，或检查 Origin/Fetch Metadata，并增加全局出站并发限制。
- 所有输入提供 :focus-visible 样式；axe 无严重焦点问题。

### P2-22 构建、测试、CI 与可观测性没有形成发布门禁

证据：

- Web build 在页面数据阶段依赖可用 PostgreSQL，当前无临时 DB 的普通 runner 会失败；本次只验证了“数据库不可达时失败”，没有验证迁移/seed 完成且数据库可达时的完整 build。
- 90 个生产 TS/TSX 文件对应 15 个测试文件，这只能说明测试分布较稀疏，不能推导行或分支覆盖率；89 个现有测试多数集中在纯函数和局部模块。
- 无数据库、migration、Route Handler、React、浏览器 E2E、fetcher cycle、AI transport 集成测试。
- vitest include 只匹配 .test.ts，未来 .test.tsx 默认不执行。
- coverage provider 和 threshold 缺失。
- 仓库没有任何 CI 配置。
- 没有 /api/health、抓取新鲜度、失败源、AI 错误率、备份失败等指标和告警。

修复与验收：

- CI 启动临时 PostgreSQL，运行 migrate deploy + seed，再执行全 workspace lint/typecheck/test/build/smoke。
- 增加 integration、E2E、compiled smoke 和 migration-from-previous-release。
- include 覆盖 test.tsx，配置覆盖率 provider 和逐步提高的门槛。
- 增加 liveness/readiness、结构化日志、cycle/digest/AI/DB 指标和告警。
- 空 runner 上一条 pipeline 能从安装到生产 smoke 全部完成。

### P2-23 抓取解析与 AI 输入上下文低于“全文摘要”预期

证据：

- apps/fetcher/src/sources/rss.ts:7-11 注册了 content:encoded，但摘要构造在 31 行没有读取该字段。
- packages/ai/src/enrich.ts:63-70 实际只发送标题和最多 600 字的 Feed snippet，不抓取文章正文。
- apps/fetcher/src/sources/chinese-media.ts:43-48 没有 summary，中文 scrape 的 enrichment 基本只依据标题。
- apps/fetcher/src/http.ts:33-38 对外部 JSON 只做 TypeScript 类型断言；Hugging Face 响应没有运行时 schema。
- scoring.ts 的 Signals 注释提及 Reddit upvotes/comments，但 RSS 实现只提取 HN 信号。

影响：

- 当前能力应准确描述为“标题/Feed snippet enrichment”，不能当作阅读全文后的摘要。
- encoded-only Feed 会丢失最丰富的正文片段。
- 上游坏 shape 可在深层访问、日期或持久化阶段才失败。
- 中文列表抓取的摘要质量和重要度判断依据尤其薄弱。

修复与验收：

- 正确读取 content:encoded，并使用可靠 HTML-to-text 与长度上限。
- 为需要高质量摘要的源增加受控 Readability/full-text 抓取策略，明确版权、超时、SSRF 和成本边界；否则文档明确只使用 Feed snippet。
- 为 RSS/Hugging Face 外部响应增加运行时 schema。
- 增加 encoded-only RSS、HF 坏 shape、Reddit 信号和中文标题-only fixture。
- UI/文档不得把 snippet enrichment 宣称为阅读全文摘要。

### P2-24 HN 和 GitHub 的“AI 过滤”会显著污染热榜

证据：

- packages/db/src/seed.ts:101-108 命名为 Hacker News (AI filter)。
- URL 实际是通用 frontpage?points=100。
- apps/fetcher/src/sources/rss.ts:17-57 只提取 HN points/comments，没有 AI 主题过滤。
- apps/fetcher/src/sources/github-trending.ts:6-15 对 "ai"、"ml" 做任意位置 includes。

影响：

- HN 的普通高分科技、商业新闻全部进入 AI Article 语料。
- email、maintain、tailwind 等普通仓库会因包含 ai 子串误命中。
- 非 AI 内容消耗受配置上限约束的 LLM 预算，并稀释热榜和 Digest；该问题主要属于内容质量和成本效率，因此列为 P2。

修复与验收：

- HN 使用明确主题查询或基于 token/metadata 的轻量分类器。
- GitHub 使用单词边界、topic、description 和负例词典。
- 保存过滤原因和抽样指标，建立 precision/recall fixture。
- email-client、maintainer-tool 等固定负例不命中；LLM、machine learning、AI agent 等正例稳定命中。
- 以标注样本设最低 precision/recall 门槛。

## 9. P3：低优先级与维护问题

- apps/web/app/source/[slug]/page.tsx 自己追加“· Hot AI”，根 metadata template 还会再次追加，标题可能重复品牌。
- sitemap 没有明确 revalidate，所有 lastModified 都使用当前时间，不能表达真实更新时间。
- feed query 的 min_importance 只检查 finite，未限制 0 到 1。
- SSRF 的 DNS timeout Promise 成功后没有清理 timer；高请求量会留下短期多余 timer。
- DNS pin 只选择第一条公共答案，无 IPv6 连通性时可能不回退 IPv4。
- Feed/Readability 固定 UTF-8 解码，GBK、ISO-8859 等声明编码可能乱码。
- stripHtml 不解 HTML entity，摘要可能显示字面 &amp;。
- Reader/Nook 外部图片由浏览器直连，可能泄露访问者 IP/Referer；HTTP 图片在 HTTPS 页面会被拦截。
- SearchBox 主表单没有完整无 JavaScript 提交语义。
- not-found 对所有 404 都提示“可能超过 14 天”，普通拼写错误时误导。
- NEXT_PUBLIC_SITE_NAME 定义于 .env.example，但 SITE.name 在 constants.ts 中硬编码。
- SITE.url 未统一去除尾斜杠，错误配置可能生成双斜杠 canonical/feed URL。
- Header、Footer、CategoryNav、HotList 等组件未挂载，且含旧首页语义。
- getCuratedBlogSlugs、getArticlesByIds 当前未使用。
- 多个静态资源没有引用，应在确认设计资产归属后清理。
- public/sw.js 没有注册代码；若历史版本曾注册同 URL，反而需要明确卸载策略。
- Nook 无限加载只依赖 IntersectionObserver，没有手动“加载更多”fallback。
- Digest 用 createdAt 充当刷新时间，应增加 updatedAt。
- revalidate 对 401/500 只打印状态，不纳入 cycle 失败。
- AI JSON fallback 只尝试第一个开括号，前置 [note] 可令后面的合法 JSON 被错过。
- PER_SOURCE_LIMIT 没有被所有抓取器一致使用。
- Hugging Face Papers 在 Source URL 不匹配特定路径时回退硬编码 URL，数据库 URL 不是真正单一配置源。
- Vite 输出 CJS Node API 弃用警告。
- Next telemetry 未在 CI/生产显式关闭。

## 11. 分阶段修复与改进路线图

### 11.1 总体原则

1. 先止血，再补状态和约束，最后做产品增强。
2. 数据库变更采用 expand-contract，不直接删除旧字段或批量不可逆重写。
3. 所有外部输入在入口校验，所有高风险输出在 sink 再次 fail-closed。
4. 任务状态必须可重试、可观测、可人工恢复，不能用一个时间戳同时表示“成功”和“永久失败”。
5. 发布门禁必须覆盖生产 Node、真实 PostgreSQL migration 和编译产物运行。
6. 每项修复必须同时提交自动化验收和文档更新。

工时假设：人日包含实现、自动化测试、代码评审修订和同步文档，不包含供应商日志等待、凭据轮换传播、DNS/证书生效、生产审批和发布窗口等待。日历周期按 3 到 4 名工程师可并行工作估算；单人执行时，日历时间大致接近总人日。

全部阶段合计约 62.5 到 88.5 人日。按安全止血、可靠性、产品语义、质量门禁顺序执行，并由 3 到 4 人并行，较现实的整体日历周期约为 4 到 7 周。

- 删除或更新 Header、Footer、CategoryNav、HotList、未使用查询和静态资源。
- 明确卸载历史 service worker，或真正实现 manifest + 注册；二者不能保持当前半状态。
- 最后统一 README、CLAUDE.md、design、nook-merge、deploy 文档。

## 12. 数据迁移与回滚策略

### 12.1 数据库

- 所有新字段先 nullable，先部署兼容读写，再回填，再加约束。
- 不在同一个 release 中删除旧列、重命名关键 enum 或重写全部 Article。
- retention 修复上线前先执行只读统计，输出过期、未来、非法 URL 和 skipped 数量。
- 对非法 URL 首先禁用点击并标记 quarantine，不在未备份时直接删除。
- 搜索索引使用 CREATE INDEX CONCURRENTLY 或等价低锁方案。

### 12.2 AI

- 新状态机上线时保留旧 aiAnalyzedAt/aiModel 作为审计字段。
- 回填 skipped 时设置分批速率，避免一次性重放导致成本尖峰。
- promptVersion 和 model 写入每条结果，回滚时可以只重跑受影响版本。

### 12.3 发布

- 每个版本放在独立 release 目录，current 只做原子 symlink 切换。
- 回滚只切回上一 release；数据库必须保持向后兼容至少一个版本。
- fetcher 先 drain，再切换；Web readiness 成功后才移除旧实例。

### 12.4 配置

- .env 不进入 release，不由 git pull 覆盖。
- 配置 schema 版本化；新增必填项先提供兼容默认和启动告警，再在下一版本强制。
- 第三方 AI 开关默认拒绝，回滚也不能恢复到预填 relay。

## 13. 最低自动化验收清单

### 13.1 安全

- Feed、Article、crossPosts、Digest 的危险 scheme 矩阵。
- NAT64、IPv4-mapped、198.18、重定向私网、DNS rebinding。
- XFF 伪造、多代理可信 hop、10 万键内存上限。
- 大 JSON、慢 body、超大 chunked body、跨站 proxy。
- CSP、安全头和键盘焦点。

### 13.2 数据与 AI

- 429/5xx/timeout 重试和最大 attempts。
- 两个 worker 的 lease/claim。
- Digest 恰好 4 条和输入 URL 白名单。
- cutoff 前后 1ms、未来日期、Invalid Date。
- persist 全失败/部分失败、Source degraded。
- contentHash 变化后的 AI requeue。
- HN/GitHub 过滤 precision/recall。
- canonical 顺序稳定、NFKC、crossPosts 多来源。

### 13.3 Web

- 无 JavaScript 首页含文章。
- AI disabled 时不存在可提交 Ask。
- Ask abort、quota reservation、citation snapshot、截断 SSE。
- Digest 坏 JSON、DB/provider 故障、禁用开关。
- Search total、分页、相关度和前进后退。
- OPML 每个 xmlUrl 可解析。
- ISR 延迟 hydration 无 mismatch。
- 320、375、768、1024 宽度和 axe。

### 13.4 发布与灾备

- Node 20 production-only fetcher dist smoke。
- 空数据库 migrate deploy + seed。
- 上一版本 schema snapshot 升级。
- 版本化 release 发布与失败自动回滚。
- fetcher SIGTERM drain。
- 备份校验与空库恢复。

## 14. 建议发布门槛

Phase 0 完成后：可继续内部测试，但不建议扩大公开流量。

Phase 1 完成后：可进入受控 Beta，需启用成本、Source 和数据库告警。

Phase 2 与 Phase 3 完成后：才具备一般生产发布条件。

### 14.1 任何环境的部署门槛

以下任一条件不满足时，连内部部署也应阻止：

- .env.example 或实际模板仍包含非空第三方 AI 配置，secret/env 文件权限不符合要求。
- 任意危险 URL scheme 可进入 href。
- 现有 unit test、Web lint 或全 workspace typecheck 失败。
- production build 或 production-only Web/fetcher dist smoke 失败。
- 生产流程不是 migrate deploy，或 HTTP -> certificate -> TLS bootstrap 尚未验证。
- 瞬时 AI 失败仍被终态化且无法按策略重试。

### 14.2 受控 Beta 门槛

除 14.1 外，必须满足：

- Phase 0 和 Phase 1 全部退出条件完成。
- Ask 可取消，可信代理 IP 已验证，额度可原子预留，LLM 并发受控。
- retention、AI retry、持久化失败和双 cycle 防重的关键集成测试通过。
- 基础备份可无人值守运行，并已完成一次空库恢复和应用读写 smoke。
- 最小 liveness/readiness、DB、Source 新鲜度和 AI 成本告警已启用。

### 14.3 一般生产门槛

除 14.1 和 14.2 外，必须满足：

- Phase 2 和 Phase 3 退出条件完成。
- 全量 integration、E2E、migration compatibility、build 和 smoke job 绿色。
- 最近 30 天内完成加密备份恢复演练，备份完整性检查、RPO/RTO 和恢复后应用 smoke 全部达标。
- 版本化原子发布和回滚在定义的压测窗口内没有部署引入的 5xx/连接中断。

## 15. 最终审计结论

Hot AI 的产品骨架和大部分功能路径是真实的，值得继续修复，而不是推倒重写。尤其是 SSRF 的逐跳校验、DNS pinning、Readability DOMPurify、URL/arXiv 归一化、评分重算、AI importance 回写、Feed 缓存和 89 个通过的单元测试，说明代码已经具有一定工程基础。

问题集中在“信任边界、失败状态、跨进程一致性、生产产物和运维闭环”五个方面。当前文档多次把设计目标写成已实现硬约束，导致风险比普通未完成功能更高：系统会静默给出“成功、已分析、今日、全文、硬保留、零停机”等错误信号。

因此建议保留现有架构，严格按 Phase 0 -> Phase 1 -> Phase 2 -> Phase 3 推进。最先要做的不是增加新页面，而是关闭第三方 AI 默认路由、统一外链协议校验、修复限流身份、把 AI/持久化失败改成可重试状态，并建立真正可运行的生产构建与数据库集成门禁。
